# Multi-file GGUF import — v0.5.5

## Architecture

The existing `ModelManager` owns model discovery and filesystem registration; this feature extends that system rather than adding a second database. The app already stores managed GGUF files in its private `filesDir/models` directory because the native engine needs a real filesystem path for its direct-I/O expert-streaming path. Incomplete split imports live outside that directory under `.incomplete-split-imports/`, so normal model discovery cannot expose them to the selector or native loader.

Each pending group has a `manifest.properties` file with a stable hash-derived ID, display/base name, expected shard count, present shard indices, per-shard private paths and sizes, aggregate imported size, architecture and available identity metadata, import status, and the last validation error. A complete group receives a durable manifest under `.model-manifests/` with status `READY`, the first-shard path, per-shard paths, count, indices, total size, and custom display name. Manifests are written through a temporary file and rename where supported.

## Import and validation

The Models screen continues to use Android's multiple-document picker. The user may choose one or multiple files; for split names the importer copies each selected source in 4 MiB chunks to an app-private staging directory, synchronizes the file, checks the known byte size, and deletes unfinished `.part` files on a handled failure/cancellation. The original SAF-selected files are never deleted. After a process kill, completed staging shards and their manifest remain; stale `.part` files are discarded and the user can add the incomplete set's missing shards later. Because completed shard bytes are copied into app-private storage during that interaction, no retained SAF permission is needed to use already-imported shards after restart.

Recognized split names use llama.cpp's numbered suffix: `name-00001-of-000NN.gguf`. The importer rejects malformed suffixes, more than 65,535 shards (the current native loader stores the count in `uint16_t`), duplicate indices, conflicting totals/prefixes, mixing ordinary models with shards, and MTP/draft or `mmproj` auxiliary names. Per shard it checks GGUF magic and parses the metadata and tensor descriptor table only; it does not read tensor weight payloads. The first shard must supply `general.architecture` and `split.count` matching the filename. Every shard must supply the zero-based `split.no` required by this vendored loader (`0` for filename index 00001) and a readable, non-empty tensor descriptor table. Additional shards may legitimately have sparse metadata: this project's vendored `llama.cpp` quantizer writes the global model metadata only to the first shard, while later shards commonly contain `split.no`, `split.count`, `split.tensors.count`, and their own tensor descriptors. Accordingly, later shards are not incorrectly required to repeat architecture or model-name keys; any overlapping architecture/identity/shape metadata is compared and conflicts are rejected. When `split.count` or `split.tensors.count` exists on a shard it is checked for consistency. An incomplete set is never registered as a loadable model.

**Format limitation:** GGUF split files do not provide a universal, guaranteed unique checkpoint fingerprint repeated in every shard. If a later shard has sparse metadata and its present keys are compatible, local header validation cannot cryptographically prove that it came from the exact same checkpoint. The importer rejects filename/metadata contradictions and validates each shard's structure; the native loader is the final compatibility check during a real load.

On completion, the validator re-checks every shard through the existing split-set check and then renames each staged shard into `models/` without concatenating or rewriting weights. The original shard filenames are preserved. The ready manifest associates the first-shard path with the logical model and a display name; renaming a model changes only that manifest's display name, not the filenames llama.cpp needs.

## Native loading

The app's current native loading path calls `llama_model_load_from_file` on the selected model path. The bundled llama.cpp source documents the `-00001-of-000NN.gguf` naming convention, requires `split.no=0` on the entry shard, discovers the remaining split files from the first-shard path, and validates the count and each additional shard's `split.no`. The app therefore passes the canonical first-shard path after all pieces are staged and validated; no concatenation and no separate JNI API were added. The copy importer normalizes the suffix casing into the canonical names used by this loader.

## Tests and validation boundary

The added/updated `ModelManagerTest` cases cover one logical entry after incremental import across a new manager instance, four shards selected out of order, duplicate shards, conflicting totals both during an incomplete import and against a ready model, incompatible `general.name`, incomplete imports being non-loadable/removable, zero-based `split.no` enforcement, truncated tensor headers, storage insufficiency before opening the stream, loss of access to a later source while retaining prior shards, stale manifest-temp cleanup, and recovery after process death mid-promotion. Existing model deletion, rename, registration, and projector tests remain in the run.

A local host-side Kotlin compilation/test harness (Kotlin 1.9 plus minimal Android/JUnit stubs) passed **40/40 supplemental test methods**: 30 `ModelManagerTest` cases and 10 `GgufInspectorTest` cases. This is not the project's actual Gradle/JUnit test task. The Gradle wrapper could not download Gradle 8.9 because `services.gradle.org` was not resolvable in this environment. Therefore the Android APK build, Compose compilation/runtime, CMake/NDK integration, actual model load through JNI, SAF behavior on a physical Android device, and the end-to-end real-native split load have **not** been verified here. The no-copy external-path flow remains separate: it can register a fully present set in an accessible filesystem folder but does not support incremental copying/staging.
